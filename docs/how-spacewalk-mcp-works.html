How spacewalk-mcp works

A Cloudflare Worker, its Rooms, a web page and a model cooperate so that a person can drive Spacewalk’s 3D chromatin viewer from a conversation, and so that anyone given the Room link can watch and change the same view. This document shows what each part is, which wires join them, and what crosses each wire.

The parts and the wires

The Host’s requests to the Worker come from Anthropic’s or OpenAI’s servers, not from the person’s computer. That is why the Worker needs a public https:// address, and why a Worker running on a laptop cannot be tried in those Hosts without a tunnel.

Two things carry the whole design. First, the Room, not the Viewer, is the record of what is shown. Each Room holds one versioned viewer state. A tool call and a person’s hand change are both proposals, which only the Room applies, and every Viewer is a replica that draws what the Room broadcasts (ADR 0001). So a change takes effect even with no Viewer open. Second, the Worker draws nothing and cannot reach a Viewer by itself. Spacewalk runs only in the Viewer, a web page, which fetches its .sw files itself and opens a WebSocket to the Room named in its Room link. The Room sends every version down that socket.

So a change from the model crosses two wires on the way out (A, then B) and the same two on the way back, the second time as a Viewer’s report that it has realized the version. Everything else in the figure exists to set those wires up, to feed Spacewalk its ensembles, and to carry the two things a Room deliberately does not keep: the camera and the highlight.

Three wires are missing on purpose. The Worker never serves the Viewer: anything but /mcp and /ws is answered 404, and the page comes from its own site. The Join card never holds the 3D viewer: the Host’s sandbox forbids framing another site, so the card carries a link and a button and nothing more. And a Viewer never calls /mcp and never talks to another Viewer: it reaches the Worker, and the other Viewers, only through its Room’s socket.

One Room id, three ways in

A Room ties one conversation to the Viewers showing its 3D view. It is a Cloudflare Durable Object, one per Room id, and the id is ten Crockford base32 characters, short enough to sit in a Room link and long enough to be unguessable. A tool call can name its Room in two ways, and open_viewer has a third. The Worker takes the first it finds.

ChatGPT sends x-openai-session on every request. The Worker turns it into a Room id with HMAC-SHA256 under the SESSION_HMAC_SECRET secret, so one ChatGPT conversation always comes to the same Room, and the raw value never appears in a link. Claude sends no such header.

The Room id comes from the model on every call because the Worker keeps no MCP session: each request is answered by a fresh MCP server and then forgotten. The model is the one thing that stays with the conversation, so open_viewer’s reply tells it to pass the id as room on every later call.

open_viewer accepts any well-formed id. A live Room keeps what it holds, so opening it again gets the same view back. An id never opened before opens that Room, empty, which lets a Connector that composes several servers mint the id itself. Every other tool refuses a Room that was never opened, so a mistyped id is caught there.

Scenario: “open Spacewalk”

The person types “open Spacewalk”. The model calls open_viewer, and a few steps later the Viewer shows an empty scene, in step with its Room. Only the first step involves the model.

WireWhat happens
1AThe Host posts tools/call for open_viewer, with no room the first time. Before that it has posted initialize and tools/list, which the Worker answers like any request, storing nothing.
2The Worker takes the Room id it was given, or ChatGPT’s, or mints a new one, and asks that Room to open. A Room never opened starts at version 0 with Spacewalk’s defaults and nothing loaded; a live Room keeps what it holds. Either way it now expires a day after its last use.
3AThe Worker replies with the Room link, https://spacewalk-viewer-dev.pages.dev/viewer.html?room=7KQ2M9XA4T, the Room id and the viewer state. The reply tells the model to open the link in Claude desktop’s built-in browser if it has one, and in no other browser tool; to pass the Room id on every later call; and to repeat neither to the person. No Viewer is contacted.
4A, GA Host that renders MCP Apps reads the Join card from the Worker and hands it the result. In Claude desktop the card says Spacewalk is opening in the panel on the right, and offers Open Spacewalk in case it does not; elsewhere it says Spacewalk is ready. Other Hosts show the text link.
5The model opens the Room link in Claude desktop’s Side panel. Where it cannot, the person presses Open Spacewalk, and the card asks the Host to open the link; Claude desktop routes it to its Side panel. Where a Host has no Side panel, the link opens in a browser tab, and everything after works unchanged.
6CThe Side panel fetches viewer.html from its static site: Spacewalk’s 3D viewer filling the window, with no navbar, no IGV and no Juicebox.
7BThe Viewer reads the Room id from its own address and opens a WebSocket to /ws?room= on the Worker it was built for. The Worker refuses any Origin not on VIEWER_ORIGINS and hands the socket to the Room. The Viewer sends join with its protocol version, and the Room answers with state: the viewer state at its current version.
8BThe Viewer draws that state, here nothing loaded and Spacewalk’s default viewer settings, and reports version 0 realized. The Room keeps the report.
A Room link opened later, in the Side panel again or by a Guest in any browser, repeats steps 6 to 8 and nothing else. The model is not involved and is not told, except that its next reply counts one Viewer more.

A Viewer that joins draws the Room’s current version, whatever it is. That is how a reload, a reconnect and a Guest arriving late all come to show the same view: each is a resync, and none of them restores anything of its own.

Scenario: “load the A549 example”

With Spacewalk open, the person asks for the A549 example. The model calls list_example_ensembles, which reads the full app’s Load From List along E, finds the A549 file’s URL there, and calls load_ensemble with it. The second call travels out along A and B, and its answer returns along the same wires, carrying the whole viewer state with it.

WireWhat happens
1AThe Host posts tools/call for load_ensemble with url and room. The Worker reads the Room id, in any case and with spaces trimmed, and refuses one that is malformed.
2The Worker proposes {type: load-ensemble, url} to the Room. Every command tool does exactly this; each is one row of server/src/commandTools.ts. The Room applies the proposal to its viewer state, gives the result version 1, and stores it before anything is drawn.
3BThe Room broadcasts version 1 to every Viewer in the Room. The Worker waits up to 20 s for the first Viewer to report it realized.
4DThe Viewer sees an ensemble it is not showing and fetches the .sw file from its URL, directly from the ensemble host, not through the Worker. Spacewalk builds the structure at the ensemble’s default group and trace, and frames it.
5BThe Viewer reports version 1 realized: drawn, and whether the ensemble is made of traces or is a point cloud. The Room keeps the report and records the kind in the viewer state, without a new version.
6The Room hands the outcome to the Worker. A later report of the same version, from a second Viewer, changes nothing, except that a failure is kept whichever Viewer reports it.
7AThe Worker replies “Applied and drawn. Version 1.”, then what changed since the model’s last reply that it did not cause, how many Viewers are connected, and the whole viewer state. The model turns it into its answer.
Some changes name a direction, not a value: step_ball_radius, step_stick_radius and adjust_background. The Room applies each to whatever the value is when it arrives, so the model need not read first, and the change cannot race a person’s hand change.

The reply always carries the whole viewer state because the model cannot see the screen. Each answer tells it what is there now, and what changed that it did not cause, so its next call can build on the view rather than on its memory of it.

Nothing more crosses B after step 5. The Room wrote version 1 itself, so a Viewer has nothing to report back but that it drew it.

When a person changes the view

The person also works in the Viewer directly: stepping to another trace, switching the render style, changing the structure appearance or the viewer settings in the Viewer’s panels. None of this goes through the model, and the model is not told at once.

Each hand change is a proposal too. The Viewer sends it to the Room along B and keeps nothing of it. The Room applies it as it would the model’s, gives the result a new version, keeps a note of it for the model, and broadcasts the version to every Viewer, the one that made the change included. That Viewer draws a state it already shows, which changes nothing. A slider or a color being dragged is sent once, a quarter of a second after it stops, the patches merged. And the change listeners that fire while a Viewer is drawing a version are taken for the echo they are, and not sent.

When the Room refuses a hand change, for instance a render style for an ensemble it knows to be a point cloud, it tells only that Viewer why and sends it the current version again, which puts the change back.

The model learns of hand changes in one of two ways: in the reply to its next call, whatever the tool, as “Changed since your last reply, not by you: stepped to trace 12; switched to ribbon”, or by asking with read_viewer_state, which changes nothing. Each change is told once. A Viewer’s failure to draw a version is told the same way.

Several Viewers, one camera, one highlight

Anyone given the Room link can open it, in any browser, and everyone with the Room open is a Participant. The Organizer is the one whose conversation the Room belongs to; the others are Guests, with no conversation and no model. In what the Viewers show they are equals: anyone’s change counts the same, and every Viewer draws every version.

Two things on screen are not in the viewer state. The Room carries both between Viewers without keeping either.

The camera. A camera pose means something only against the geometry a Viewer has drawn, which the Room never sees, so each Viewer’s camera rig owns its pose (ADR 0005). At any moment one Viewer is the camera holder and the others follow it: the Viewer where a person last took hold of the camera, let go of it, reset it or stepped to another trace. When a person lets go, the Viewer sends its pose with the place it was read in, and the Room relays it. A Viewer showing another place drops it, and one whose own person is dragging ignores it. When the holder leaves, the longest-connected Viewer takes over.

The highlight. Pointing at the genomic navigator lights the matching part of the structure, and, with balls and sticks, pointing at a ball lights the navigator. The Viewer sends the highlight as the pointer moves, about once an animation frame, and the Room relays it to every other Viewer, which draws it as if its own person were pointing (ADR 0006). A person’s own highlight wins on their own screen. When a Viewer whose highlight is showing closes, the Room sends a clear in its place.

Neither is news to the model. The camera reaches it only through get_shareable_url, which asks the holder for a reading of that moment, and the highlight not at all.

Calls that are not a plain change

Of the 14 tools, seven are command tools and follow Figure 4. load_session follows it too, once it has read its session. The other six never change the viewer state.

ToolWiresWhat the Worker does
open_viewerAOpens the Room, minting an id if it is given none, and builds the Room link. Sends the Viewers nothing.
list_example_ensemblesA, EReplies with the example list, group by group, each ensemble with its name and URL. Needs no Room.
read_viewer_stateAReplies with the viewer state, the number of Viewers connected, and what changed that the model did not cause. Sends the Viewers nothing.
read_viewer_countAReplies with the number of Viewers connected and nothing else, leaving the news for the model’s next reply, so a Connector can poll it to show whether Spacewalk is open.
get_shareable_urlA, B, FRefuses when nothing is loaded. Takes the camera pose from a load no Viewer has drawn yet, or else asks the camera holder for a reading, waiting up to 3 s. Writes a snapshot URL and shortens it; if shortening fails, replies with the long one.
reset_cameraA, BNot a proposal: the Room tells every Viewer to frame the structure, and waits up to 3 s for the holder to confirm. No version is made.
load_sessionA, F for a short URL, then BReads the Spacewalk block of a shareable URL or session string and proposes it whole, as one change, so a Viewer draws it once. A short URL is followed to its long one; a session is never fetched from a URL. The reply says what was left out, such as IGV tracks and the Hi-C map.
A snapshot URL has no Room. It opens viewer.html with a session block and the viewer settings in its parameters: a frozen view that later changes in the Room do not reach. To bring someone into the Room itself, give them the Room link.

The example list finds ensembles; it does not load them. The model passes the URL it picked to load_ensemble, a command tool, and each Viewer fetches the file along D.

What each part keeps

The table says what survives between requests, and where. The Room is the record of what is shown; each Viewer is a replica of it, and owns only its camera pose.

PartKeepsFor how long
The modelThe Room id, in the conversationAs long as the conversation
The HostNothing about the Room. ChatGPT sends the same x-openai-session on every request of a conversationAs long as the conversation
Worker, at /mcpNothing per request: each gets a fresh MCP server. Per Worker instance, the example listFive minutes, then fetched again
RoomThe viewer state and its version; the latest version a Viewer has realized, and the last 100 failures reported; the last 100 changes the model did not cause, until a reply tells them; a loaded session’s camera pose, until a Viewer has drawn the load. On each socket: when it joined, whether it holds the camera, and whether its highlight is showingDeleted a day after its last use, whether or not Viewers are connected; the Room then keeps only its last version number, marked expired
Join cardThe Room linkAs long as the conversation shows it
ViewerWhat it last drew; its camera pose; the reference ruler’s position on screen, and which panels are open. Nothing in localStorageUntil the page closes; the view, though not the pose, is drawn again from the Room when the Room link is opened again

A Room is used by a tool call, or by a Viewer joining, proposing, reporting a version or moving the camera; a highlight alone does not count. An expired Room never gets its contents back. open_viewer with its id starts it again, empty, at the version after its last, so that no Viewer takes the new state for one it has already drawn. Only a snapshot URL taken from the Room outlasts it (ADR 0004).

A Viewer that reloads or reconnects draws the Room’s current version and frames the structure, then takes the holder’s pose if another Viewer holds the camera. A lone Viewer that reloads therefore loses its orbit and shows the framing. Nothing has to enforce one Viewer per Room.

When something goes wrong

What happensWhereWhat the model or the person sees
A call’s room is not a Room idAThe Worker refuses it, and says to pass the Room id from open_viewer’s reply.
A call carries no room and no x-openai-sessionAAn error that says to pass room. Only open_viewer mints an id instead.
Only x-openai-session arrives, and the secret is not setAThe request fails as a server misconfiguration. There is no fallback key.
The Room was never openedA, BThe tool says to call open_viewer. A Viewer opened on that link shows “There is no such Room.” and does not retry.
The Room has expiredA, BThe tool says what the Room showed is gone, and to call open_viewer with that room to start it again, empty. A Viewer shows “This Room has expired.” and does not retry.
A proposal does not apply, such as choosing an ensemble group with nothing loadedAAn error with the reason, followed by the viewer state and the news. Nothing changes.
No Viewer is openBNot an error: “Applied, not shown yet — no viewer is open.” The next Viewer to join draws it.
No Viewer reports within 20 sB“Applied, still drawing. How it came out will be in a later reply.” A later reply says how far the Viewers have realized.
A Viewer cannot draw a version, such as a .sw file it cannot fetchB, D“Applied, but the Viewer failed to draw it”, with the reason. The version stands in the Room, and that Viewer does not try the same place again until the Room names another.
The example list cannot be readEAn error that says to try later, or to ask the person for the URL of a .sw file.
The shortener failsFThe long snapshot URL, which works as well.
A short URL given to load_session cannot be followedFAn error that says to ask the person for the long URL.
The camera holder does not answer within 3 sBget_shareable_url gives a snapshot that opens framed, and says why. reset_camera says no Viewer confirmed it.
The Viewer speaks another protocol versionB“This viewer is out of date: reload the viewer.” The Room closes the socket.
The Viewer’s socket dropsBNothing is shown. The Viewer rejoins after 1 s, 2 s, up to 5 s, and draws the current version. A hand change made meanwhile is not sent, and the resync puts it back.
The Viewer is served from an origin not on VIEWER_ORIGINSBThe socket is refused with 403, and the Viewer keeps retrying.

Addresses

These are the development deployment, the only one running. Both parts run on one Cloudflare account, the one that owns the 3dg.io zone. They are deployed as a matched pair: the Worker names the Viewer page in VIEWER_URL and admits it in VIEWER_ORIGINS, and the Viewer page is built with the Worker’s address in VITE_SERVER_URL, fixed at build time. Production, spacewalk-mcp.3dg.io with spacewalk-viewer.pages.dev, is configured the same way and not yet deployed.

Locally the Worker runs on localhost:8787 and the Viewer page on localhost:5173, from the spacewalk repo’s Vite dev server. The Viewer connects to the Worker directly, since VITE_SERVER_URL defaults to localhost:8787, and the local VIEWER_ORIGINS admits localhost:5173. The local VIEWER_URL in wrangler.toml names the root, where the full app ignores ?room=, so a working local Room link needs VIEWER_URL pointed at /viewer.html with wrangler dev --var.

The words used here (Viewer, Room, Room link, Participant, Organizer, Guest, viewer state, structure appearance, camera pose, framing, camera holder, highlight, session, session block, snapshot URL, proposal, relative step, realized) are defined in GLOSSARY.md. A Host is the Claude or ChatGPT app, and the Side panel is Claude desktop’s built-in browser pane. The decision to make the Room the record of the view is ADR 0001; to keep viewer settings beside the session, ADR 0002; to keep spacewalk-remote and the protocol in this repo, ADR 0003; to keep both the Room and the session, ADR 0004; to give the camera to the Viewer’s rig, ADR 0005; and to relay the highlight without keeping it, ADR 0006. How the repos and packages fit together is in How spacewalk-mcp fits together, and where each part is deployed on Cloudflare, and from which source, is in How spacewalk-mcp is deployed.
