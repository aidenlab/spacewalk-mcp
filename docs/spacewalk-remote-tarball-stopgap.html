The spacewalk-remote tarball stopgap

What a tarball is, what we set up on October 30, 2026, and how to work with it until the package is on npm.

In one paragraph: an npm package is just a compressed file with a name attached. npm normally looks up the name and downloads that file for you. We can't publish to the @aidenlab scope yet, so we put the same file on a GitHub release and told spacewalk to download it from there. To the viewer code, it's the same package either way.

Your one rule: once a tarball is released, never replace it. A change means a new version and a new release.

What a tarball is

A tarball is one file that holds a folder. It's built in two steps, which is where the double extension comes from:

  • tar joins many files into one, keeping their names and folders.
  • gzip compresses that one file. The result is .tar.gz, or .tgz for short.

It's the same idea as a .zip file, using the format Unix and npm have standardized on. There's nothing else inside: no installer and no special npm wrapping, only the files.

Here is everything in ours, aidenlab-spacewalk-remote-0.1.0.tgz, 8.6 kB in total:

package/LICENSE
package/package.json        name, version, and dependencies (zod)
package/README.md
package/src/attachRemote.ts
package/src/index.ts
package/src/protocol.ts

npm requires the top-level package/ folder, and npm pack adds it for you. The list of what goes in comes from the files field in remote/package.json, which is why the tests and config aren't included.

What npm does, and what we changed

When you install a package by name, the registry only helps you find the file. It then hands back a tarball like ours. We skip the lookup and go straight to the download:

Normal install, from the npm registry
You ask for a name and version
The registry finds that version's .tgz URL
npm downloads the .tgz
npm unpacks it into node_modules
Our stopgap, from a GitHub release
You give the .tgz URL directly
No lookup needed
npm downloads the .tgz
npm unpacks it into node_modules

You can see the registry's half of this with a real Aiden Lab package. This prints a URL ending in .tgz:

npm view @aidenlab/juicebox-remote dist.tarball

Because the end result is the same, imports don't change. import { attachRemote } from '@aidenlab/spacewalk-remote' resolves through node_modules, and it can't tell where the files came from.

Rules while this is in place

Never replace an attached tarball. spacewalk doesn't commit its lockfile, so nothing would notice a swapped file. Two people could install the same URL and get different code.

Don't start the tag with v. A v* release triggers publish-remote.yml, which tries to publish to npm. Use remote-0.1.1, not v0.1.1, until npm access is sorted out.

Remember it's a snapshot. Merging a change to remote/ doesn't reach the viewer. The viewer only sees it after a new release and a new pin. That includes wire protocol changes, so if the server's protocol changes, the viewer needs the new tarball before it deploys.

Common tasks

Look inside a tarball

This lists the contents without unpacking anything:

tar -tzf aidenlab-spacewalk-remote-0.1.0.tgz

To preview what the next tarball would hold without creating it, run this from spacewalk-mcp:

npm pack --workspace remote --dry-run

Try unreleased changes to remote/ locally

Run this from spacewalk. It links your local copy without changing package.json:

npm install ../spacewalk-mcp/remote --no-save

The next plain npm install may put the released tarball back, so rerun this if your local changes seem to disappear.

Release a new version

  1. In spacewalk-mcp, bump the version on a branch, then merge it to main by pull request: 
    npm version 0.1.1 --workspace remote --no-git-tag-version
  2. From an up-to-date, clean main, build the tarball and release it: 
    npm pack --workspace remote --pack-destination ~/Desktop

gh release create remote-0.1.1 \
  ~/Desktop/aidenlab-spacewalk-remote-0.1.1.tgz \
  --repo aidenlab/spacewalk-mcp --target main --prerelease \
  --title "spacewalk-remote 0.1.1 (stopgap tarball)" \
  --notes "Stopgap until the package is on npm."
  3. In spacewalk/package.json, change the version in both places in the URL, then run npm install and commit.

Switch to npm when access arrives

  1. Get publish rights for the @aidenlab scope and set up the trusted publisher, as your spacewalk-npm-todo.txt note describes. The first publish may have to be done by hand.
  2. Publish a release tagged v plus the current version in remote/package.json, such as v0.1.0. The workflow fails if the two don't match.
  3. In spacewalk/package.json, replace the URL with the plain version: 
    "@aidenlab/spacewalk-remote": "0.1.0"
  4. Run npm install, confirm the build, and commit.

You can leave the stopgap release in place afterward. Older spacewalk commits pin its URL, so deleting it stops them from installing.
