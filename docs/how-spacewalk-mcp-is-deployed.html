How spacewalk-mcp is deployed

Everything spacewalk-mcp runs on is in one Cloudflare account. This document says what each kind of Cloudflare object is, which ones exist, and where each part of the spacewalk-mcp and spacewalk repos ends up: what ships it, what it lands in, and where its code finally runs.

The Worker, the Room, the Viewer, the Join card and the wires between them are described in How spacewalk-mcp works, which this document assumes. That one is about what happens while someone uses it. This one is about what has to be put where beforehand.

The kinds of Cloudflare object

Cloudflare hosts several kinds of thing, and spacewalk-mcp uses five of them. Two words from the other document are worth separating out first. A Room is a Cloudflare object: one Durable Object. A Viewer is not. Cloudflare only serves the Viewer page’s files; the Viewer itself is that page running in a person’s browser.

KindWhat it isOurs
AccountThe unit of ownership and access. Everything below belongs to exactly one account, and a wrangler login must be able to reach it to change anything.The Aiden Lab account, 1eadb18b…902e. server/wrangler.toml names it, so a login that reaches several accounts does not have to choose.
ZoneA domain whose DNS Cloudflare runs. Cloudflare can then point the zone’s hostnames at its Workers and Pages projects and issue their certificates.3dg.io and aidenlab.org, both in that account.
WorkerA program Cloudflare runs on its own servers when an HTTP request arrives, in the data center nearest the request. It has no machine or disk of its own, many copies may run at once, and nothing in memory is guaranteed to last from one request to the next. What is uploaded is one bundled JavaScript file plus its settings: a name, its addresses, variables, secrets and bindings.spacewalk-mcp-dev, from server/. Also Spacewalk’s sw-shortlink, the link shortener, from the spacewalk repo.
Custom domain, routeThe two ways a hostname reaches a Worker. A custom domain gives the Worker a whole hostname; Cloudflare makes its DNS record and certificate. A route claims a pattern, such as one path, on a hostname that something else serves.spacewalk-mcp-dev.3dg.io is a custom domain, and the Worker has no other address: no workers.dev hostname and no preview URLs. spacewalk.aidenlab.org/shorten is a route.
Durable ObjectA class a Worker exports, whose instances Cloudflare creates by name. There is exactly one instance per name anywhere in the world, it handles one thing at a time, and it has storage of its own that lasts, and an alarm it can set. So every request for one name meets in one place, which lets an instance hold many WebSockets and keep one record for all of them. A Worker reaches the instances through a binding.The class Room, bound as ROOM: one instance per Room id, made the first time the id is used. It keeps the viewer state in its storage (SQLite-backed), holds every Viewer’s socket, sleeping between messages without dropping them, and its alarm deletes what it holds a day after its last use.
Pages projectA static website: files Cloudflare serves exactly as uploaded, at project.pages.dev and any custom domains. Each upload is a deployment, and the latest one on the production branch is the live site. Files arrive either by direct upload, with wrangler pages deploy, or by Cloudflare building a connected GitHub repo. None of its JavaScript runs on Cloudflare: it all runs in the browser that loads it.spacewalk-viewer-dev, the Viewer page, uploaded directly. Also spacewalk, the full Spacewalk app, built from GitHub.
R2 bucketObject storage: files under names, read over HTTP. A bucket can be made public at an r2.dev address.spacewalk-fixtures: the example .sw files and load-from-list.json.
Variables, secretsSettings a Worker reads when it runs. Variables are written in wrangler.toml and anyone with the repo can read them. Secrets are set with wrangler secret put and cannot be read back. A directly uploaded Pages project has neither, so a page’s settings must be built into its files.VIEWER_URL and VIEWER_ORIGINS; the secret SESSION_HMAC_SECRET. The page’s one setting, VITE_SERVER_URL, is built in.
Workers Logs are on for the Worker in both environments: whatever the Worker and its Rooms write with console is kept and searchable in Cloudflare’s dashboard, and wrangler tail --env dev streams it live.

The Worker and the Room come from the same upload but run differently. The Worker’s code runs wherever a request lands and forgets it, which is why each MCP request builds a fresh MCP server and why the model has to name its Room on every call. Each Room runs in one place, chosen near where it was first used, and every tool call and every Viewer’s socket for that Room id is handed to it there. That difference is the reason the Room, not the Worker, is the record of what is shown.

What the account holds

The shortener refuses the dev Viewer page today. Its ALLOWED_ORIGINS lists spacewalk-viewer-dev.3dg.io, a hostname nothing serves, and not spacewalk-viewer-dev.pages.dev, the origin the Worker sends. A POST with that origin answers 403, so on dev get_shareable_url always gives the long snapshot URL. Production’s spacewalk-viewer.pages.dev is not listed either.

Only the two objects on the left are spacewalk-mcp’s. Of the three on the right, the Worker reads load-from-list.json from the bucket (wire E in the other document), each Viewer fetches .sw files from it (wire D), and the Worker posts to the shortener (wire F). The full app is drawn because its hostname carries the shortener’s route, and because the spacewalk repo builds it from the same source as the Viewer page.

From source to Cloudflare

Read Figure 2 across. Each row starts with files in one of the two repos, goes through the command that ships them, lands in a Cloudflare object, and ends where that code actually runs. The last column is the one that most often surprises: a Pages project runs nothing, and the Join card, uploaded inside the Worker, runs in the Host.

Five things in the figure are easy to get wrong.

  1. One upload, two kinds of runtime. room.ts is not deployed separately. It is in the same script as index.ts, which exports the Room class, and the [[migrations]] entry in wrangler.toml tells Cloudflare to run that class as Durable Objects. One wrangler deploy replaces the code of the Worker and of every Room at once; what the Rooms have stored is kept.
  2. The Join card ships with the Worker but runs in the Host. joinCard.ts is a string of HTML inside the Worker. A Host that renders MCP Apps reads it with resources/read and runs it in a sandboxed frame in the conversation. It loads its MCP Apps client from unpkg.com, not from Cloudflare.
  3. The Viewer page is built in one repo and shipped by the other. Its source is all in spacewalk, but scripts/deploy-dev.sh in this repo builds and uploads it, so that the Worker and its page are always deployed by the same script, with matching addresses. The spacewalk repo has no deploy of its own for the Viewer page.
  4. The Viewer page’s project serves the full app too. vite build always builds both pages, index.html and viewer.html, so spacewalk-viewer-dev.pages.dev/ is the full app. It ignores ?room=, which is why VIEWER_URL must end in /viewer.html.
  5. A Pages project runs nothing. All of Spacewalk, all of spacewalk-remote and roomAttachment.js run in the browser. Cloudflare’s part in a Viewer ends once its files are sent; after that, the Viewer’s only tie to Cloudflare is its socket to the Worker, which Cloudflare hands to the Room.

Where spacewalk-remote lands

The remote/ folder has no deployment of its own and does not exist as a separate thing once deployed. It lands in two places, by two different routes, and the two copies can differ.

In the Worker and the RoomsIn the Viewer page

Which copyThe remote/ folder as it stands when wrangler deploy runs, through the npm workspace linkThe version spacewalk/package.json pins, downloaded from npm by npm install

The two meet only at runtime, over the socket, and the check that they agree is the protocol version a Viewer sends in join. deploy-dev.sh refuses to upload a Viewer page built from a locally linked remote/, so a deployed page always holds a published version. How the package is versioned and published is in How spacewalk-mcp fits together and Releasing spacewalk-remote.

A matched pair

The Worker and the Viewer page are two uploads to two different objects, and each must be told the other’s address. The Worker reads its side when it runs; the page has its side built into its script.

SettingSet inLands inSays
VIEWER_URLserver/wrangler.toml, [env.dev.vars]The Worker, as a variableThe Viewer page to put in a Room link: https://spacewalk-viewer-dev.pages.dev/viewer.html
VIEWER_ORIGINSThe sameThe Worker, as a variableThe only origins whose sockets /ws accepts: https://spacewalk-viewer-dev.pages.dev
VITE_SERVER_URLdeploy-common.sh, from the script’s BASE_URLThe page’s script, as text, at build timeThe Worker a Viewer opens its socket to: https://spacewalk-mcp-dev.3dg.io
SESSION_HMAC_SECRETNowhere in source: deploy-common.sh stores 32 random bytes if it is missingThe Worker, as a secretThe key turning ChatGPT’s x-openai-session into a Room id. Changing it moves every ChatGPT conversation to a new Room, so the script never replaces it

Because VITE_SERVER_URL is baked in, a built page belongs to one Worker. A direct upload never sees a Pages project’s own variables, so the script passes the address to the build and then checks that the built script contains it before uploading. Changing which Worker a page talks to means building and uploading the page again.

The Worker goes live first. If a release raises the protocol version, Viewers are told “This viewer is out of date: reload the viewer.” until the page upload finishes, and reloading does not help until then.
